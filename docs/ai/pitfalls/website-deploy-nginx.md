# Website, Deploy, systemd und nginx — Pitfalls

- **CSS-Spezifität schlägt Klassen-Reihenfolge — Dark-Logo schien im Hell-Schema durch (verifiziert 2026-10-19, #39):** In `website/index.html` stand `.logo img { display: block }` (Spezifität 0,1,1) vor `.logo-dark { display: none }` (0,1,0). Das `block` der ersteren gewann, das Dark-Logo war in **jedem** Schema sichtbar; weil beide PNGs das Radl an derselben Pixelposition tragen, sah man im Hell-Schema ein zweites, „freistehendes" Radl unter dem Logo (im Dark-Schema unsichtbar, da deckungsgleich). Fix: Sichtbarkeit auf gleiche Spezifität legen — `.logo img.logo-<variante>` für beide Zustände **und** für den `[data-theme="dark"]`-Override. Rezept zur Diagnose: `getComputedStyle(img).display` je Ergebnis von `data-theme` prüfen, nicht dem Screenshot trauen.
- **`tsx` ist im Produktions-Install Pflicht — `node server/index.js` gibt es nicht (verifiziert 2026-10-29, #51):** `app/server/index.ts` ist TypeScript, das Repo hat keinen Server-Bundler. Der Dienst startet deshalb über `node node_modules/tsx/dist/cli.mjs server/index.ts`; `tsx` steht in `dependencies` (nicht `devDependencies`), `vite` dagegen nur in `devDependencies` und wird ausschließlich im Dev-Modus dynamisch geladen. Wer `npm ci --omit=dev` vergisst bzw. `tsx` nach `devDependencies` verschiebt, bekommt `Cannot find module …/tsx/dist/cli.mjs`.
- **`sudo npm ci` legt `node_modules` mit 0700 an → Dienst stirbt mit EACCES (verifiziert 2026-10-29, #51):** root hat umask 077. Der Dienst-User (`kik-app`) kann dann weder `node_modules/tsx/...` lesen noch starten; das Symptom (`Cannot find module`) sieht wie ein fehlendes Paket aus. Fix im Deploy: `umask 022` vor `npm ci` und `chmod -R a+rX` über `/srv/kik-app/app`; das Skript prüft die Lesbarkeit danach explizit mit `sudo -u kik-app test -r`.
- **`rsync -a src/dir dest/dir` ohne trailing Slash verschachtelt (verifiziert 2026-10-29, #51):** `rsync -a app/server /srv/kik-app/app/server` legt `app/server/server/` an — der Dienst findet `server/index.ts` nicht. Immer `"$SRC/" "$DEST/"` schreiben. Gleiches Muster bei `install -d`: ein `install -d <ziel>` vor einem späteren `mv <ziel>.tmp <ziel>` macht aus dem `mv` ein Verschieben *in* das Ziel.
- **`systemd` `Environment=%d` wird expandiert — `EnvironmentFile=` für Secrets nicht (verifiziert 2026-10-29, #51):** `Environment=PORTAL_ENV_FILE=%d/portal.env` landet als `/run/credentials/kik-portal.service/portal.env` im Prozess (Credential-Dateien werden dem Dienst-User 0400 übereignet). `/etc/portal/portal.env` bleibt 0600 root und ist damit auch für `grafg` unlesbar — Migrationen deshalb als root mit `PORTAL_ENV_FILE=… /usr/local/bin/npm run db:migrate`.
- **`scripts/deploy-app.sh` darf nicht als root laufen (2026-10-29, #51):** Ein root-Lauf hinterlässt root-eigene Dateien in `app/dist`; danach scheitert der nächste Deploy als normaler Nutzer an den Rechten. Das Skript verweigert den root-Start deshalb — Deploy immer als `grafg`, nur der Symlink-Swap und der nginx-Teil brauchen `sudo`.
- **Node liegt nur unter nvm — systemd sieht es nicht (2026-10-29, #51):** `~/.nvm/versions/node/v24.21.0/bin` ist nur in interaktiven Shells im PATH (`.bashrc`). Job-Runner, systemd-Units und Subagenten brauchen entweder den expliziten PATH oder das systemweite Node unter `/usr/local/node24` (`/usr/local/bin`-Symlinks). Symptom: `node: command not found` in einem Timer-Lauf, der von Hand funktioniert.
- **Öffentliche Website hängt bewusst NICHT am Node-Prozess (2026-10-29, #51):** nginx liefert die vorgerenderten Dateien direkt aus `/srv/kik-app/current/dist`; nur `/tokens`, `/api/auth/`, `/api/keys`, `/api/usage/` gehen an die App. Fällt `kik-portal` aus, bleiben alle öffentlichen Seiten online und `/tokens` zeigt eine statische Ausfallseite. Diese Trennung nicht „vereinfachen", indem man `/` an die App proxy't — sie ist die Ausfallreserve.
- **Release-Wechsel braucht keinen nginx-Reload (2026-10-29, #51):** `current` ist ein Symlink, den nginx pro Request auflöst. Rollback = `ln -sfn` + `mv -T` auf das Vorrelease; nur ein geänderter *Server-Code* braucht `systemctl restart kik-portal`.
- **Anleitung ist Vertrag: Discovery-Namen ändern sich in Text *und* Issue-Notizen (Defekt 2026-10-30, #55/#56):** Die öffentliche Anleitung (`website/content/anleitung/tokens.md`) behauptete „Ältere Konfigurationen mit `large-v3` funktionieren weiterhin", obwohl der Alias Stunden vorher entfernt worden war (`GET /v1/models` → nur `whisper-large-v3`, `model=large-v3` → 4xx, festgenagelt in `scripts/test-stt-api.mjs`). Ursache: Anleitung (#56) und Alias-Entfernung (#55) liefen am selben Abend parallel — nachgezogen wurde nur der Test, nicht der Text. Der Absatz ist ersatzlos entfernt: die Seite beschreibt ausschließlich die **Neueinrichtung**, keine Migrationen. Regel: wird ein Modell-/Discovery-Name entfernt oder umbenannt, wandern Anleitung, Issue-Notizen und PITFALLS im selben Commit mit.
- **API-Host `api.kik.spengergasse.at` hat ein eigenes Zertifikat (2026-10-29):** DNS ist ein CNAME auf `kik.spengergasse.at`; das Zertifikat des Haupt-VHosts deckt den Namen **nicht** ab. Eigene LE-Linie via `certbot --nginx -d api.kik.spengergasse.at`, Renewal über den bestehenden `certbot.timer`. Basis-URL für Clients: `https://api.kik.spengergasse.at/v1` (der Pfad `/api/` auf dem Haupt-Host bleibt als Zweitzugang).
- **`proxy_pass` ohne URI ist Pflicht, sonst frisst nginx das `/v1/` (verifiziert 2026-10-29):** Bei `location ^~ /v1/ { proxy_pass http://127.0.0.1:4000/; }` ersetzt nginx das gematchte Präfix `/v1/` durch `/` — LiteLLM bekommt `/audio/transcriptions` und antwortet 404. Richtig ist `proxy_pass http://127.0.0.1:4000;` (keine URI, Pfad bleibt) oder explizit `…/v1/`. Der bestehende `api.kik`-VHost funktioniert nur deshalb, weil seine Location exakt `/` ist und `/` durch `/` ersetzt wird.
