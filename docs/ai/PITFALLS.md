# PITFALLS — llm-on-premise

## Bekannte Fallstricke

- **Hardware-Entscheidung blockiert Setup**: Ohne finale Hardware kann vLLM-Konfiguration nicht abgeschlossen werden
- **ROCm vs. CUDA**: AMD-Optionen sind günstiger, aber ROCm-Ökosystem ist weniger ausgereift als CUDA
- **Gemma 4 Lizenz**: Apache 2.0, aber SuperGemma 4 Uncensored ist ein Community-Derivat – Policy für Schulumgebung klären
- **SSO-Integration**: Auth hängt an Schul-IdM – Koordination mit ZID nötig
- **Tool Calling Zuverlässigkeit**: Nicht alle Modelle liefern konsistentes Function Calling für SearXNG – evaluieren vor Deployment
- **Preise veralten schnell**: Hardware- und API-Preise ändern sich monatlich. Alle Preisangaben mit Datum versehen (DOMAIN.md). Stand 2026-06-24 als Referenz notiert.
- **China-Datenschutz**: DeepSeek, SiliconFlow, Kimi, GLM sind chinesische Anbieter. DSGVO-konformer Betrieb ungeklärt. On-Premise oder EU-Anbieter (Hetzner, OVHcloud, Gcore, Mistral) sind der sichere Weg.
- **China-Datenschutz — Lösung via EU-Router (2026-08-13)**: Direkt-APIs von DeepSeek/SiliconFlow/Kimi/GLM sind **Tier 4** (nicht DSGVO-konform): Daten auf chinesischen Servern, kein EU-Controller/Zwischenstufe, italienische Garante-Sperre bei DeepSeek. Lösung: EU-Router wie **Cortecs** (Tier 1, Wien, EU-native Clouds Scaleway/OVH/IONOS, ISO 27001, DPA, No-Training) hostet dieselben Modelle EU-souveran. Siehe `docs/extern/cortecs-provider-evaluation.md` für vollständige DSGVO-Tier-Klassifikation (Tier 1: Cortecs, Azure OpenAI; Tier 2: Anthropic/OpenAI/Together/Fireworks; Tier 3: OpenRouter; Tier 4: Direct-China).
- **ChatGPT Edu-Preis unsicher**: Quellen widersprechen sich ($10/Schüler/Jahr vs. $10/Schüler/Monat). Letzteres angenommen für Berechnungen. Vor Vertrag klären.
- **GPU-DRAM-Preisschock**: LPDDR5x-Knappheit hat DGX-Spark- und Hetzner-Preise 2025/26 steigen lassen. Temporär, aber aktuell real.

## Strom / PCIe-Anschlüsse

- **6+2-Pin ist ein 8-Pin**: Die 2-Pin-Sektion wird auf den 6-Pin aufgesteckt – das ist der bestimmte, sichere 8-Pin-PCIe-Anschluss. Kein Adapter nötig, kein „Hack".
- **Keine Y-Splitter von einem PSU-Anschluss auf zwei Kartensockel**: Überlastet die einzelne Leitung → Schmelz-/Brandgefahr. Lieber beide separaten PCIe-Stränge des Netzteils nutzen (je einen pro Sockel).
- **PCIe- vs. EPS/CPU-6→8-Adapter**: Pinout unterschiedlich. EPS-Adapter in eine GPU gesteckt = Karte zerstört. Nur PCIe-Adapter verwenden.
- **Netzteil-Alterung**: VX550W (CMPSU-550VX, ~2008) – Kondensatoralterung, fehlende moderne Schutzschaltungen. Für unattended-Betrieb langfristig austauschen.

## LiteLLM / opencode / models.dev-Proxy

- **LiteLLM `:main-stable` akzeptiert KEIN SQLite**: `database_url: sqlite://...` ist *fatal* (Container crash-looped). Postgres ist Pflicht (bundled im compose-Service `db`).
- **opencode entdeckt KEINE Modelle für Custom-`@ai-sdk/openai-compatible`-Provider automatisch**: der `provider.models`-Plugin-Hook wird nur gefeuert, wenn der Provider zur Hook-Zeit in der `database` ist; Config-Provider werden erst *nach* dem Hook-Loop gemerged (`packages/opencode/src/provider/provider.ts:1398`). Workaround: Provider via models.dev-Proxy in den Katalog *injizieren*, damit er in der `database` lebt → Hook feuert nicht nötig (Katalog liefert Modelle direkt). Upstream: opencode Issue #6231.
- **Config-Overlay hält Katalog-Modelle**: `provider.ts:1400-1407` übernimmt `existing.models` aus dem Katalog und mergt nur `options` (baseURL/apiKey) — daher `{ "options": {...} }` ohne `models`-Block funktioniert. Verifiziert via A/B (mit `OPENCODE_MODELS_URL` → 7 Modelle, ohne → 0).
- **LiteLLM `async_pre_call_hook` bekommt `call_type="acompletion"`** (nicht `"completion"`) für `/v1/chat/completions`. Gating-Sets in Custom-Plugins MÜSSEN die async-Varianten (`acompletion`/`atext_completion`/`aembedding`) enthalten.
- **LiteLLM-Counter-Korruption**: ein in `async_pre_call_hook` geworfenes `HTTPException(429)` löst `async_log_failure_event` für denselben (ungezählten) Request aus. Zähler per `litellm_call_id` matchen — abgelehnte Requests nie in die `_counted`-Menge aufnehmen, sonst korrupt der Globalzähler den aktiven Modell-Status.
- **LiteLLM-Callback-Registrierung**: `litellm_settings.callbacks: [module.attr]` — nur eine *Instanz* (nicht die Klasse) wird an `litellm.callbacks` dispatcht; `_callback_capabilities` (`proxy/utils.py:1601`) überspringt Strings, die nicht zu bekannten Callback-Namen resolven. Instanz-Form `single_gpu_guard.guard` (mit `guard = SingleGpuGuard()` auf Modulebene) funktioniert; Klassen-Form nicht.
- **`models.dev/api.json` liefert 403 Forbidden** bei Pythons Default-urllib-User-Agent im Datacenter/Container (Cloudflare-Bot-Protect). Browser-artige UA (`opencode-models-proxy/1.0`) liefert 200 mit 151 Providern. Proxy muss UA setzen, sonst fehlen alle Built-Ins (anthropic/openai/…) und nur litellm bleibt → opencode verliert alle Standardprovider.
- **`OPENCODE_MODELS_URL` ersetzt den Katalog KOMPLETT**: der models-Proxy gibt Upstream + litellm-Injektion zurück; fällt der Proxy aus, nutzt der Client seine Disk-Cache-Datei (letztgültig). Beim allerersten Start ohne Cache + toter Proxy → leerer Katalog → schlimmster Fall; Proxy robuste halten (`restart: unless-stopped`).
- **LiteLLM `/v1/models` dedupliziert gleiche ollama-Manifests** (`e4b-128k` == `e4b-it-qat-128k` zeigen auf denselben Blob) — nur eins erscheint. Keine Alias-Tags duplizieren; ein logischer Tag pro Modell pflegen.
- **Gemma-4-Kontextlängen sind Architektur-Eigenschaft**: e4b/e2b = 128K nativ; 12b/26b/31b = 256K. `PARAMETER num_ctx` über die Trainings-Grenze hinaus → Qualitätsverfall jenseits der Grenze (RoPE-Positionen ungesehen in Training) + verschwendeter KV-Cache.
- **opencode-Subcommand-Gotcha**: `opencode models <provider>` (mit Argument) liefert "Provider not found" für kataloggestützte Provider; der TUI-Picker (`opencode models` ohne Arg / `/models` in TUI) funktioniert. Nur gegen den Picker validieren.
- **Docker + ufw**: `:11434` ist ein *veröffentlichter Container-Port* → ufw kann ihn NICHT filtern (Docker pflegt eigene iptables-Regeln in der DOCKER-Kette). `:11435` ist Host-Service (ollama) → ufw könnte filtern (aktuell nicht umgesetzt → Known Gap, ollama direkt ohne Auth erreichbar). Wegen Docker+ufw-Interaktion immer nur Host-Service-Ports über ufw kontrollieren.
- **`OLLAMA_KEEP_ALIVE=-1` + `MAX_LOADED_MODELS=1`**: das zuletzt genutzte Modell bleibt unbegrenzt warm; ein anderes Modell-Request löst erst durch den SingleGpuGuard (in LiteLLM) das Evict+Swap aus — ollama selbst blockt sonst beim 2. Modell (Issue ollama/ollama#14578, ~50s Serialisierung). **Keep-forever kollidiert NICHT mit idle-swap** — der Guard swapped bei `in_flight==0` automatisch; Kosten = einmalige ~50s Evict+Load bei Modellwechsel. Der 429 gilt nur für genuinely-busy (A generiert mid-stream, B wird angefordert).
- **SingleGpuGuard `in_flight`-Counter kann lecken (Wurzel des 429-Forever-Bugs)**: ein abgebrochener Streaming-Request (Client-Disconnect mid-stream, `curl --max-time`, Client-Crash) feuert u.U. KEIN `async_log_failure_event` → der in `async_pre_call_hook` inkrementierte Counter wird nie dekrementiert. `in_flight` bleibt > 0, der Guard hält das Modell fälschlich für "busy" und 429-ed jedes andere Modell **für immer** (der `_SANITY_CEILING=64`-Reset greift nicht, weil Rejects den Counter nicht inkrementieren — er bleibt bei 1 kleben). **Fix (2026-07-05): Staleness-Self-Heal** — `_Domain.last_busy_at` wird je Inkrement gestemptelt; `async_pre_call_hook` prüft `now - last_busy_at > _STALE_AFTER` (660s = `request_timeout`+60s grace) und forciert Reset+Swap statt 429 (`STALE-RESET` im guard.log). Verifiziert: geleakter Counter (via `--max-time 2`-Abort reproduziert, `in_flight` klebte bei 2) heilt nach < `_STALE_AFTER` von selbst und swapped.
- **LiteLLM `async_pre_call_hook` data.metadata.litellm_params ist NOCH LEER**: der Router wählt das Deployment (und damit `api_base`) erst NACH `pre_call`; `litellm_params.api_base` ist erst in den log-event-kwargs (`async_log_success_event`/`async_log_failure_event`) verfügbar. Wer in `pre_call` die `api_base` braucht (z.B. für `/api/ps`-Reconcile), muss sie selbst aus `config.yaml` (`model_name → litellm_params.api_base`) auflösen — SingleGpuGuard lädt die Map via PyYAML beim Start (`_load_config_map`, `/app/config.yaml`). Beide Pfade (pre_call via Map, log-event via `litellm_params`) MÜSSEN auf denselben Domain-Key konvergieren, sonst driftet der Guard-State zwischen pre_call und _adjust.
- **SingleGpuGuard muss ollama `/api/ps` reconcilen (sonst Divergenz bei Out-of-band-Loads)**: Out-of-band-Loads (`ollama run` auf dem Host, `:11435`-Direktzugriff-Bypass Issue #4) laden ein Modell, ohne dass der Guard es sieht → Guard-State und ollama-Realität divergieren. **Fix (2026-07-05):** `pre_call` pollt `GET {api_base}/api/ps` (2s-Cache `_OLLAMA_PS_TTL`, 1.5s-Timeout, via `asyncio.to_thread` damit der Event-Loop nicht blockiert); bei `in_flight==0` adoptiert der Guard ollamas geladenes Modell als Wahrheit (`RECONCILE`/`RECONCILE-EMPTY` im guard.log). Polling passiert VOR dem Domain-Lock (sonst blockiert der HTTP-Call den Event-Loop unter dem Lock). Macht den Guard korrekt unabhängig vom `:11435`-Bypass (Issue #4 bleibt für **Auth** offen, aber nicht für Guard-Korrektheit). Verifiziert: out-of-band `ollama :11435/api/generate` → nächste LiteLLM-Request zeigt `RECONCILE`+`SAME`, HTTP 200.
- **SingleGpuGuard guard.log ist append-only & bind-mounted** (`./data:/app/data`): `docker compose restart litellm` löscht die Datei NICHT — alte `REJECT`-Zeilen bleiben stehen. Für einen sauberen Trace-Nachblick `: > /opt/litellm/data/guard.log` VOR dem Restart (oder `tail -n +<mark>`). Neue Traces seit Fix: `ACCEPT`/`SAME`/`SWAP`/`REJECT`/`STALE-RESET`/`RECONCILE`/`RECONCILE-EMPTY`/`SANITY-RESET` (vorher nur `REJECT`+`init`).
- **LiteLLM `/v1/models` ist KEY-SCOPED, nicht Router-Katalog** (`proxy_server.py:8054` `model_list()` → `get_available_models_for_user`): der Endpoint liefert die `models`-Allowance des API-Keys, nicht `config.yaml` `model_list`. Eine Virtual Key mit hartcodierter `models`-Liste **pinnt den sichtbaren Katalog** unabhängig davon, was `config.yaml` oder ollama anbieten — selbst Modelle, die im Router gar nicht (mehr) existieren, werden advertised (Calls darauf failen dann zur Laufzeit mit „model not found"). Diagnose: `/model/info` zeigt den echten Router-State (was `config.yaml` definiert), `/v1/models` zeigt die Key-Sicht. Beide vergleichen — stimmen sie nicht überein, pinnen die Keys den Katalog. Fix: `models` der Keys auf `'{}'` setzen (erben den Proxy-Katalog) ODER die Listen pflegen. **LiteLLM discoverd KEINE ollama-Tags automatisch** — die früher vermutete „Auto-Discovery" war ein Zufallstreffer (Key-Liste == ollama-Katalog zum Key-Erstellungszeitpunkt). Quelle der Wahrheit für den Katalog ist `config.yaml` `model_list`, geladen am Startup.
- **Virtual-Key-`models`-Änderung via direktem SQL flusht NICHT den Key-Cache**: LiteLLM cached Keys in-memory (`user_api_key_cache`, TTL-basiert). Ein `UPDATE "LiteLLM_VerificationToken" SET models='{}'` in Postgres wird erst nach Cache-Expiry oder **`docker compose restart litellm`** sichtbar. Sauberer (ohne Restart): `POST /key/update` via API invalidiert den Cache direkt — braucht aber den Master-Key + den vollen Key-Value. Für host-lokale Wartung ist SQL+Restart pragmatisch.
- **ollama speichert Blobs als `sha256-<hex>` (Bindestrich), nicht `sha256:<hex>` (Doppelpunkt)** auf Disk: Manifest-Digests nutzen Doppelpunkt, Dateinamen Bindestrich. Beim direkten Blob-Handling (Copy/Inventory/Restore) Filename als `sha256-<hex>` konstruieren, sonst `FileNotFoundError`. Verify per `sha256sum datei == <hex>`.
- **`ollama rm` GCt nur jetzt-unreferenzierte Blobs**: beim Entfernen eines Tags prüft ollama, ob die referenzierten Blobs noch von anderen Tags genutzt werden — nur wirklich verwaiste werden gelöscht. Deduplication ist damit gratis: zwei Tags mit denselben Weight-Blobs (z.B. `e4b-128k` = `e4b-it-qat` @128K) teilen sich einen Blob; `ollama rm` eines davon lässt den Blob erhalten, solange das andere existiert. Vor Massen-`rm` die Shared-Blob-Matrix via Manifest-Cross-Reference berechnen (Python über `~/.ollama/models/manifests/**`) — unique Blobs ggf. in ein Inventory kopieren, shared bleiben unangetastet. Siehe `/opt/litellm/blob-inventory/README.md` für die gregor-Beispiel-Pipeline.
- **Qwen3-Thinking frisst kleine `max_tokens`-Budgets (kein Bug, verifiziert 2026-09-17, Issue #17)**: Qwen3 (getestet qwen3:8b) generiert erst ~100+ Tokens Thinking selbst bei trivialen Prompts („Sag Hallo." → ~500 Zeichen Thinking). Via LiteLLM `/v1/chat/completions` mit kleinem `max_tokens` (20/100/200) ist das Budget aufgebraucht bevor Content entsteht → Antwort-`content` leer bei `finish_reason=stop`, kein `reasoning_content`. Direkt an ollama `/api/chat` sichtbar: `content=''`, `thinking` voll. **Fix**: Budget ≥ ~500 für Smoke-Tests, oder Thinking clientseitig deaktivieren (`think=false`; Open WebUI macht das via Model-Params). Modelfiles im Repo lassen Thinking bewusst an (Client kontrolliert) — nur Open WebUI schaltet es ab.
- **Whisper (3,8 GB VRAM, resident) verdrängt große LLM von der GPU (verifiziert 2026-09-17, Issue #17)**: Whisper-Container (`hwdsl2/whisper-server:cuda`) hält ~3,8 GB VRAM dauerhaft → qwen3:8b (7,4 GB Bedarf) lädt nur **39 % der Layer auf GPU** (`ollama ps` → `61%/39% CPU/GPU`), Rest CPU → GPU-Util 0 %, alles langsam. **Fix**: `docker compose stop whisper` (stop, nicht down — Restart via `up -d whisper`), Modell entladen (`ollama stop <tag>`), neu laden → **100 % GPU, 58 tok/s** (7,4 GB von ~7,7 GB nutzbar — knapp, passt). Faustregel 8-GB-GPU: Whisper + max. EIN 8B-Modell schließen sich gegenseitig aus — SingleGpuGuard sieht nur LiteLLM-Traffic, Ollama-Direktlast + Whisper-Konkurrenz per Disziplin managen.
- **Whisper dauerhaft deaktiviert (2026-09-17, Issue #17 — STT kommt künftig via GROQ)**: `restart: "no"` in `compose.yaml` (live + Repo synchron) + `DELETE whisper-1` aus LiteLLM-DB. Restore bei Bedarf: `docker compose up -d whisper` + DB-INSERT (`model_id=whisper-1`, `model=openai/whisper-1`, `api_key=whisper-sk-gregor-2026` aus `/opt/litellm/.env`, `api_base=http://whisper:9000/v1`, `model_info={}`) + `restart litellm`. Katalog danach wieder 7 Modelle. GROQ-Whisper wird später ein eigener DB-Eintrag (andere api_base + echter API-Key).
- **LiteLLM-Streaming liefert KEINE `tool_calls`-Deltas für ollama-Modelle (verifiziert 2026-09-17, 1.91.0 UND 1.101.0, Issue #18)**: Non-Streaming funktioniert (korrekte `tool_calls`, Tool-Auswahl, 2. Turn). Im Stream kommen stattdessen `content`-Fragmente mit dem Tool-Call-JSON (`{"name": "calculator", …}`) und `finish_reason=stop` — Clients (opencode, Open WebUI) sehen `{}`/Müll statt Tool-Calls. **Root-Cause präzisiert (war früher „Open-WebUI-Stream-Handler")**: ollama selbst streamt native `tool_calls`-Frames (verifiziert an `/api/chat`: Thinking-Deltas, dann 1 Frame mit `tool_calls:[{id, function}]`, dann `done:true`) — **der LiteLLM-Proxy demotiert sie zu Content-Text**. Weder `think:false` via `extra_body` noch das 1.91.0→1.101.0-Upgrade ändern das. Upstream-Referenzen: PR #11171 (Streaming-Parse, Mai 2025), Issue #11262 (fehlende Tool-Call-ID), PR #11528, Issue #6135. **Workaround**: keiner außer Non-Streaming-Clients; Tool-lastige OpenCode-Workflows bis zum Upstream-Fix meiden bzw. ohne Tool-Erwartung nutzen. Guard ist unschuldig (ACCEPT/SAME-Traces normal).

## Open WebUI

- **`base_model_id` muss `NULL` sein, nicht `''` (empty string)**: Open WebUI's Model-Merge-Logic (`utils/models.py:144`) prüft `if custom_model.base_model_id is None` — nur `None` (nicht `''`) triggert den Override-Pfad, der `model['info']` mit unseren Capabilities/Params setzt. Bei `''` wird der elif-Zweig genommen, der die Custom-Model-Entry **überspringt** (`continue`), wenn die Model-ID bereits im LiteLLM-Katalog existiert → Base-Model wird OHNE Capabilities verwendet → `builtin_tools` defaultet zu `True` → Model outputet Tool-JSON `{}`. **Fix**: `UPDATE model SET base_model_id = NULL WHERE base_model_id = '';`. Models die via Admin-UI erstellt wurden, haben korrektes `None`; nur SQL-inserted Models haben dieses Problem. Siehe `docs/ai/TIPS.md` für Full-Diagnose.
- **LiteLLM `store_model_in_db=true` ohne DB-Migration**: das Toggle `store_model_in_db` in LiteLLM speichert nur die Config-Setting, migriert aber NICHT die `config.yaml`-Modelle in `LiteLLM_ProxyModelTable`. Die Modelle erscheinen im UI (aus einem Cache), aber die Edit-Seite hängt (Loading-Spinner) und `/model/new` timed out. **Fix**: Modelle manuell per SQL in `LiteLLM_ProxyModelTable` eintragen, dann `docker compose restart litellm`.
- **LiteLLM `model_info` muss `supports_function_calling: false` setzen**: ohne `model_info` (leer `{}`)Advertising LiteLLM Function-Calling-Support an Open WebUI → Open WebUI registriert Tools → Models outputen `{}`. Set per SQL: `UPDATE "LiteLLM_ProxyModelTable" SET model_info = '{"supports_function_calling": false}' WHERE model_name IN (...);`
- **`10.8.0.18` ist eine tote IP (verifiziert 2026-09-17, Issue #16)**: gregor war 2026-07 auf `.18`, heute ist gregor `10.8.0.16` (VPN/tun0). `10.8.0.18` hat keinen DNS-Eintrag und keine Route → alle `api_base`/baseURL/URLs darauf zeigen sind tot (Inference via LiteLLM kaputt, Katalog leer/stale). **NIE `10.8.0.18` verwenden.** Referenz-Orte die beim VPN-IP-Wechsel synchron zu pflegen sind: `/opt/litellm/.env` (LITELLM_PUBLIC_URL), `~/.config/opencode/opencode.json` (baseURL, mcp SEARX_URL), `~/.bash_aliases` (OPENCODE_MODELS_URL), LiteLLM-DB `LiteLLM_ProxyModelTable.litellm_params.api_base`, Repo-Templates (`litellm/*.example`, `.env.example`, README.md, opencode-env.sh, models_proxy.py).
- **`host.docker.internal` ist NICHT auflösbar im litellm-Container** (kein `extra_hosts` im compose): `http://host.docker.internal:11435` failt. Stattdessen gregors VPN-IP `10.8.0.16:11435` verwenden (vom Container aus erreichbar). Kein DNS-Eintrag → IP ist der Wartungspunkt.
- **opencode-Modellliste kann stale sein, obwohl LiteLLM korrekt ist (Issue #16)**: zwei Ebenen können stale sein — (a) LiteLLM-DB `LiteLLM_ProxyModelTable` (DB-mode: `/v1/models` liest aus der DB, `model_list` in `config.yaml` leer), (b) opencode-Disk-Cache `~/.cache/opencode/models*.json` (unconditional serviert, bei Fehlschlag still refreshed). Fix: DB-Zeilen per SQL update/insert/delete + `sudo docker compose up -d --force-recreate litellm models-proxy` (flusht Keys + Env) + `rm -f ~/.cache/opencode/models*.json`. Verifikation in frischem Terminal: `opencode models` zeigt die 6 gregor-Modelle unter `litellm/`.
- **Open WebUI: keine Builtin-Tools ohne UI-Session + `builtin_tools`-Capability (verifiziert 2026-09-17, Issue #21)**: Native-FC-Tool-Injektion (`search_web` etc.) erfordert ALLE drei: top-level `session_id` im Request (API-Caller ohne UI-Session bekommen KEINE Tools — by design), `function_calling != 'legacy'` und `capabilities.builtin_tools=true`. Unser Capability-Lockdown setzte `builtin_tools=false` → **auch bei `web_search=true` findet keine Suche statt**. Web-Search-Modelle brauchen zwingend `builtin_tools=true` + Tool-Noise-Reduktion via `meta.builtinTools` (KB/Notes/Automations/Time off). Details + e2e-Rezept in TIPS.md („Native Tool-Call Mechanics").
- **Open WebUI: native Tool-Call-Loop nur im Streaming-Pfad (verifiziert 2026-09-17, Issue #21)**: Non-Streaming-Requests bekommen die ollama-`tool_calls`-Antwort stillschweigend gedroppt (kein 2. Turn, kein Search, keine Fehlermeldung). `stream: true` im e2e-Test setzen. Zudem verlangt der Background-Fanout top-level `id` (Assistant-Message-ID) — ohne sie läuft nichts (`task_ids: []`). Synthetische `chat_id` ohne DB-Row → `'NoneType' object has no attribute 'get'` → Loop crasht nach Tool-Ausführung; erst Chat via `POST /api/v1/chats/new` anlegen.
- **Ollama `OLLAMA_MAX_LOADED_MODELS=1` funktioniert (verifiziert 2026-09-17, Issue #21)**: Laden eines zweiten Modells evicted das residente (auch bei `KEEP_ALIVE=-1`) — `/api/ps` zeigt danach nur das neue. Damit ist die Single-Residency doppelt abgesichert (Env-Limit + speicherbasiertes Ollama-Swapping). Direkt-Traffic ist trotzdem Single-Residency-sicher.
- **Open WebUI: `reasoning_tags=true` killt die Builtin-Tool-Injektion (verifiziert 2026-09-17)**: `qwen3:8b-search` mit `params.think=true + reasoning_tags=true` bekommt KEINE Tools injiziert (`prompt_eval_count` 546 statt ~2000, kein `search_web`-Call, Modell behauptet „kein Zugang zu Echtzeitdaten") — `use_builtin_tools`-Pfad greift nicht. Mit `think=true + reasoning_tags=false` funktioniert Thinking+Search kombiniert (Reasoning → `search_web` → 2. Reasoning über Results → Antwort mit Citations, e2e-verifiziert). Merksatz: **Thinking einschalten via `think`, aber `reasoning_tags` auf `false` lassen**, sonst ist das Suchmodell taub.
- **Open WebUI LDAP ist search-then-bind — kein Direct-Bind (verifiziert 2026-09-24, Issue #22)**: `routers/auths.py:ldap_auth` bindet IMMER zuerst den App-Account (`ldap.server.app_dn`, sonst ANONYMOUS), sucht den User, und bindet erst dann mit dem eingegebenen Passwort. Es gibt keinen Config-Schalter für „direkt mit den eingegebenen Credentials binden". Hat der AD keinen anonymen Read (oder kein `app_dn` gesetzt), findet die Suche nichts → Login unmöglich, egal wie korrekt das Passwort ist.
- **Dieser AD erlaubt anonymen Bind, aber KEINEN anonymen Read (verifiziert 2026-09-24)**: auf LDAPS 636, LDAP 389 und GC 3268 gelingt `anonymous` bind, aber `(objectClass=user)`-Suchen liefern **0 Einträge**. Ohne Service-Account ist Open WebUI-LDAP damit tot.
- **AD maskiert fehlende Leserechte als `noSuchObject` (nicht `insufficientAccess`)**: eine falsche Base-DN und ein reines Rechte-Problem sehen identisch aus (`0000208D NameErr ... NO_OBJECT`). Selbst existierende DNs (`CN=Users`, das Service-Account-OU) liefern anonym `noSuchObject`. Base-DN daher NUR mit dem Bind-Account verifizieren, nie anonym.
- **Open WebUI `ldap.server.search_filter` ist ein ZUSATZfilter, kein Login-Template**: der Code baut `(&(<attribute_for_username>=<login>)(<search_filter>))`. `{{login}}` wird **nicht** substituiert — der frühere Wert `(sAMAccountName={{login}})` ergab `(&(uid=<login>)(sAMAccountName={{login}}))` und matchte nie. Korrekt: `(objectClass=user)`.
- **Open WebUI Login-Default + Toggle (v0.11.4)**: `mode = enable_ldap ? 'ldap' : 'signin'`; der „Continue with Email/LDAP"-Toggle rendert nur `{#if enable_ldap && enable_login_form}` und benennt das **Ziel** (nicht den aktuellen Modus). Um den Toggle loszuwerden, muss genau eine Methode aktiv bleiben: LDAP-only → `ui.enable_login_form=false`; Email-only → `ldap.enable=false`.
- **`WEBUI_AUTH_TYPE` und `LDAP_BASE_DN` sind in open-webui v0.11.4 No-Ops**: kein Vorkommen im Image; die korrekten Keys sind `ENABLE_LDAP` bzw. `LDAP_SEARCH_BASE` (config.py). LDAP-Aktivierung steuert die DB-Key `ldap.enable`.
- **Open WebUI `Config.get`/`get_many` liest die DB pro Request**: `/api/config` baut `features.enable_ldap`/`enable_login_form` daraus (`main.py:2261,2333-2335`) → DB-Direct-Edits an `ldap.*`/`ui.enable_login_form` wirken **ohne Restart** (anders als z.B. `audio.stt.model`, wo die ConfigVar beim Start geladen wird).
- **Open WebUI LDAP matcht User per `mail`, Rolle bleibt**: existiert der User (z. B. `grafg@spengergasse.at`), wird er wiederverwendet und seine Rolle NICHT überschrieben; nur **neue** User bekommen `ui.default_user_role`.
- **Lokales Open-WebUI-Passwort neutralisieren, aber `auth.active=1` lassen**: `authenticate_user_by_email` (LDAP-Pfad) filtert `Auth.active.is_(True)`. Ein `active=0` würde den LDAP-Login desselben Users mitbrechen. Stattdessen `password` durch einen bcrypt-Hash eines Zufallswerts ersetzen (bestehender Hash war `$2b$12$`).
